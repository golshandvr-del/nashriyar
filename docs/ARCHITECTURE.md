# معماری فنی — نشریار

## ۱. محدودیت‌های تعیین‌کننده

| محدودیت | پیامد معماری |
|---|---|
| پیش‌نمایش فعلی روی لینک موقت / Cloudflare Pages | Runtime لبه (Workers): بدون `fs`، بدون پردازش سنگین، محدودیت CPU هر درخواست |
| مقصد نهایی: هاست و دامنهٔ شخصی (احتمالاً سرور داخل ایران) | کد نباید به Cloudflare قفل شود؛ همه‌چیز پشت **Adapter** |
| احتمال محدودیت/اختلال اینترنت بین‌الملل | **هیچ CDN خارجی** در زمان اجرا: فونت، آیکن، کتابخانهٔ نمودار و CSS همه self-host و bundle می‌شوند |
| نبود درگاه پرداخت | منطق فروش = مدیریت کد دسترسی + ثبت فروش دستی |
| نبود Cron در استقرار میزبانی‌شده | کارهای دوره‌ای (rollup آمار، انقضای کدها) به‌صورت **Lazy** روی درخواست‌ها یا با Cron سرور شخصی |
| AI اختیاری | لایهٔ `AIProvider` با پیاده‌سازی پیش‌فرض `NullProvider` |

## ۲. پشتهٔ فناوری

| لایه | انتخاب | دلیل |
|---|---|---|
| زبان | TypeScript (strict) در همهٔ لایه‌ها | یک زبان، نوع‌های مشترک بین سرور و کلاینت |
| سرور/API | **Hono** | هم روی Cloudflare Workers و هم روی Node.js/Bun بدون تغییر اجرا می‌شود |
| اعتبارسنجی | **Zod** (+ `@hono/zod-validator`) | اسکیمای مشترک فرم‌ها و API |
| ORM/DB | **Drizzle ORM** با گویش SQLite | روی Cloudflare D1 و روی سرور شخصی با `better-sqlite3`/`libsql` یکسان؛ مسیر مهاجرت به PostgreSQL باز |
| ذخیرهٔ فایل | لایهٔ `StorageAdapter`: R2 (پیش‌نمایش) / S3-سازگار مثل آروان‌کلاد یا MinIO / دیسک محلی | قابل‌حمل |
| فرانت‌اند | **React + Vite** (SPA) با React Router | داشبوردهای غنی و تعاملی، جامعهٔ بزرگ برای توسعهٔ بعدی |
| استایل | **Tailwind CSS** (build-time، نه CDN) + کامپوننت‌های سبک shadcn/Radix | RTL کامل با `dir="rtl"` و logical properties، تم روشن/تیره با CSS variables |
| داده در کلاینت | TanStack Query | کش، همگام‌سازی، حالت‌های بارگذاری |
| نمودار | **Apache ECharts** (self-hosted) | نمودارهای پیشرفته، پشتیبانی RTL و فونت فارسی، تم تیره |
| تاریخ | `date-fns-jalali` / `Intl` با تقویم `persian` | تقویم شمسی و بازه‌گزینی شمسی |
| فونت | **وزیرمتن** (Vazirmatn) self-hosted | خوانایی بالا، متن‌باز |
| PDF در مرورگر | **pdf.js** (فقط در پنل تیم برای تبدیل) | تبدیل PDF به تصویر صفحات در مرورگر بارگذارکننده |
| تست | Vitest (واحد/یکپارچگی) + Playwright (E2E) | |
| کیفیت | ESLint + Prettier + TypeScript check در CI (GitHub Actions) | |

## ۳. ساختار مخزن (هدف)

```
nashriyar/
├── apps/
│   ├── server/            # Hono API + سرو کردن SPA
│   │   ├── src/
│   │   │   ├── routes/    # admin/*, team/*, public/*, me/*, auth/*
│   │   │   ├── services/  # منطق دامنه (بدون وابستگی به runtime)
│   │   │   ├── adapters/  # db, storage, ai, mail, clock
│   │   │   ├── insights/  # موتور بینش قاعده‌محور
│   │   │   └── entry/     # cloudflare.ts | node.ts  (نقاط ورود runtime)
│   │   └── migrations/
│   └── web/               # React SPA (سه بخش: public, team, admin)
├── packages/
│   ├── shared/            # نوع‌ها، اسکیمای Zod، ثابت‌ها، ابزار تاریخ/اعداد فارسی
│   └── db/                # اسکیمای Drizzle (منبع واحد حقیقت پایگاه داده)
├── docs/
├── deploy/                # Dockerfile, docker-compose, nginx, systemd, اسکریپت پشتیبان
└── .github/workflows/
```

> در فاز ۰ ممکن است ساختار با یک پکیج شروع شود و در فاز ۱ به monorepo (npm workspaces) تبدیل شود.

## ۴. لایه‌بندی و قابل‌حمل بودن

```
[ React SPA ] --HTTP/JSON--> [ Hono routes ] -> [ services (دامنه) ] -> [ adapters ]
                                                                    ├─ DB: D1 | better-sqlite3 | (Postgres)
                                                                    ├─ Storage: R2 | S3 | LocalDisk
                                                                    ├─ AI: Null | OpenAI-compatible
                                                                    ├─ Mail/SMS: Null | provider
                                                                    └─ Clock (برای تست‌پذیری زمان)
```

- **services** هرگز `env` کلودفلر یا `fs` را مستقیم نمی‌بینند؛ فقط interfaceها را.
- **entry/cloudflare.ts**: adapters را از bindings (`DB`, `BUCKET`) می‌سازد.
- **entry/node.ts**: adapters را از متغیرهای محیطی (مسیر فایل SQLite، اطلاعات S3) می‌سازد و با `@hono/node-server` اجرا می‌کند.
- نتیجه: انتقال به هاست شخصی = تغییر نقطهٔ ورود + تنظیم env، بدون بازنویسی منطق.

## ۵. مسیرهای API (نمای کلی)

| پیشوند | دسترسی | نمونه |
|---|---|---|
| `/api/auth/*` | عمومی | ثبت‌نام، ورود، خروج، بازیابی |
| `/api/public/*` | عمومی | فهرست نشریات، جست‌وجو، صفحهٔ نشریه، اکسپلور، دسته‌ها |
| `/api/me/*` | کاربر واردشده | کتابخانه، ثبت کد، دنبال‌کردن، ذخیره‌ها، کامنت، پیشرفت مطالعه |
| `/api/reader/*` | کاربر دارای دسترسی | توکن جلسهٔ خواندن، تصاویر صفحات با امضای کوتاه‌مدت |
| `/api/team/:publicationId/*` | سه نقش اصلی آن نشریه | اعضا، شماره‌ها، فهرست، پیشرفت، رسانه، پست، کامنت، کد فروش |
| `/api/admin/*` | مسئول نشریات / سوپرادمین / ناظر دانشکده | همه‌چیز + آمار + بینش‌ها + ممیزی |
| `/api/track` | عمومی (محدودشده) | ثبت دسته‌ای رویدادهای بازدید |

## ۶. خط لولهٔ نسخهٔ دیجیتال امن

مشکل: پردازش PDF در Workers ممکن نیست (محدودیت CPU) و ارسال PDF کامل به خواننده یعنی امکان دانلود.

راه‌حل:

1. عضو تیم PDF را در پنل انتخاب می‌کند.
2. **در مرورگر خود او** با pdf.js: تعداد صفحات خوانده می‌شود (برای آمار صفحات)، هر صفحه به تصویر
   WebP با دو کیفیت (بندانگشتی + خواندنی) رندر می‌شود، متن هر صفحه برای جست‌وجو استخراج می‌شود.
3. تصاویر صفحات و PDF اصلی با آدرس‌های امضاشدهٔ آپلود مستقیم به Storage می‌روند.
   **PDF اصلی خصوصی است و هرگز به خواننده سرو نمی‌شود** (فقط آرشیو).
4. در سرور شخصی می‌توان این تبدیل را به یک worker سمت سرور (مثلاً `pdftoppm`) منتقل کرد.
5. خواننده: درخواست «جلسهٔ خواندن» ← بررسی مالکیت در کتابخانه ← دریافت آدرس‌های صفحات با
   امضای چنددقیقه‌ای و فقط برای صفحات نزدیک ← رسم روی `<canvas>` + **واترمارک پویا** (شماره
   دانشجویی + زمان) ← جزئیات بازدارنده‌ها در [`SECURITY.md`](./SECURITY.md).

## ۷. ذخیره‌سازی رسانه

| نوع | ذخیره | نمایش |
|---|---|---|
| PDF نشریه | اصلی: خصوصی؛ صفحات: تصویر WebP | کتاب‌خوان امن |
| صوت/پادکست | فایل MP3/OGG/M4A | پخش‌کنندهٔ داخلی؛ برای پولی: لینک امضاشدهٔ کوتاه‌مدت |
| ویدیو/کلیپ | MP4 (H.264) — فاز بعد HLS | پخش‌کنندهٔ داخلی |
| عکس/پست | WebP با چند اندازه (فشرده‌سازی در مرورگر پیش از آپلود) | اکسپلور |

- آپلود فایل‌های بزرگ: **آپلود مستقیم با URL امضاشده / multipart** به‌جای عبور از سرور اپ.
- سقف حجم و نوع MIME در سرور اعتبارسنجی و از نام فایل اصلی مستقل است (کلید تصادفی).

## ۸. آنالیتیکس

- رویدادهای بازدید سمت کلاینت **دسته‌ای** به `/api/track` ارسال می‌شوند (کاهش نوشتن).
- حذف تکرار: هر (بیننده، موجودیت، روز) یک «بازدید یکتا».
- جدول خام `view_events` + جداول تجمیعی روزانه `daily_stats_*` که به‌صورت Lazy
  (هنگام اولین درخواست آمار یا با Cron در سرور شخصی) به‌روز می‌شوند.
- داده‌های تولید (مراحل، زمان‌ها) از `activity_events` و جداول مراحل محاسبه می‌شوند.
- جزئیات شاخص‌ها: [`ANALYTICS.md`](./ANALYTICS.md).

## ۹. هوشمندی دولایه

1. **موتور بینش قاعده‌محور (همیشه فعال):** قواعد قابل‌پیکربندی روی داده‌های آماری؛
   خروجی کارت‌های «هشدار / فرصت / اطلاع» در داشبورد مسئول.
2. **AI اختیاری:** اگر کلید API در تنظیمات باشد، روی همان خروجی‌های ساخت‌یافته کار می‌کند
   (خلاصهٔ روایی، پرسش‌وپاسخ آماری، پیشنهاد کلیدواژه). خطا یا نبود کلید ⇒ UI بخش AI را
   پنهان می‌کند و هیچ مسیر دیگری تحت تأثیر قرار نمی‌گیرد. کلید فقط سمت سرور.
